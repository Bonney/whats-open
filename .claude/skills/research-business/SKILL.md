# Research a business for the guide

Produces (or updates) one file under `restaurants/<slug>-<town>.json` matching
`templates/restaurant-template.json`. Never touch `restaurants-combined.json`
— it's regenerated by CI on push to `main`.

## 1. Identify the target

- **Existing listing**: read its current `restaurants/*.json` file first. Treat
  every field as a claim to re-verify, not a given — sites go stale, places
  close, hours shift with the season.
- **New listing**: confirm it's actually in Rockland, Thomaston, Camden, or
  Spruce Head (check `restaurants/` for the town suffixes already in use) and
  isn't already a file under a different slug.
- **Refreshing many listings at once**: split into batches of ~5-6 and run
  them in parallel, giving every batch the exact same field-resolution rules
  from this skill so output stays consistent across batches. Don't let a
  batch resolve an identity question on its own (see "Watch for rebrands"
  below) — those get reconciled centrally, after the batches report back, not
  inside a batch. Likewise, don't rely on individual batches to keep
  `tags.json` in sync (see the `tags` field below) — do that as one
  reconciliation pass over everything the batches actually used, after they
  finish, so near-duplicate tags don't get invented in parallel.

## 2. Gather sources

Search the web for, in this rough order of reliability for *hours*:

1. Google Maps / Google Business listing (often the freshest, and shows
   "Hours updated by business X weeks ago")
2. Facebook page — check recent posts too, not just the About/Hours tab;
   owners often post seasonal-hours changes there before updating anything
   else
3. Instagram bio/recent posts
4. Official website
5. Online ordering platform if one exists (Toast, Square, Clover, ChowNow,
   etc.) — its listed hours are sometimes the most accurate since it gates
   ordering

**Direct fetches of Facebook/Instagram URLs frequently fail** — they render a
login wall or a client-side JS shell with no real content instead of the
page. When that happens, don't give up on the source: search for `"<business
name>" facebook hours` (or similar) and use the search-result snippet, or
fall back to an aggregator that mirrors the business's own posted info —
Yelp, Tripadvisor, Apple/Google Maps listings all frequently surface the same
hours Facebook has without needing to render the page itself.

Cross-check at least two sources when possible. If sources disagree on *any*
field — not just hours — prefer the more recently updated one and note the
discrepancy to the user rather than silently picking. If nothing resolves
confidently, leave that field as it was rather than guess.

**Watch for seasonal hours.** Coastal Maine restaurants commonly run
different hours (or open/closed status) in summer vs. off-season, and some
close entirely for winter. The schema only holds one set of weekly hours —
if a place is currently in a seasonal state, use the *current* hours and
flag to the user that seasonal variation exists so they can decide whether
to note it in the description or revisit later.

**Watch for closures.** If you find signals the business has closed
permanently (no recent posts, "permanently closed" on Maps, news mentions),
stop and flag it instead of writing/updating the file — don't guess.

**Watch for rebrands.** A business can still be open under a new name —
distinct from a closure. Signals: the file's Facebook URL now displays a
different business name, or listings under the old name have vanished while
a new name shows up at the same address/phone. This is a bigger change than
a normal field edit: it means a new `id` and a renamed file, not just an
edited value. Don't rename it yourself — flag it to the user with the
identity evidence (matching phone/address plus the new name confirmed across
at least two independent sources) and get confirmation before renaming the
`id` and file together.

## 3. Resolve each field

- `id`: `<slug>-<town>`, lowercase, hyphenated, town matching the pattern
  already used in `restaurants/` (`rockland`, `thomaston`, `spruce-head`,
  `camden`).
  For an existing listing, check that `id` actually matches the filename and
  that the slug matches the business's real name — mismatches happen (a
  filename typo, a business whose name doesn't match what's in the slug) and
  won't announce themselves. Don't silently rename to fix one; call it out in
  the report per step 5, even if you leave it as-is.
- `name`: the business's actual display name (not an SEO-stuffed title-tag
  variant).
- `description`: one or two plain sentences, matching the existing corpus'
  voice — factual and descriptive (cuisine, setting, what it's known for),
  no marketing adjectives lifted verbatim from the business's own copy. Two
  real examples from the corpus, for tone/length: "Drinks and dining with a
  view of the beautiful Rockland golf course." and "Take-out stand offering
  grilled hot dogs and burgers. Uses peanut oil. Cash only."
- `address`: street address, town, state, zip — `<street>, <Town> ME
  <zip>`, matching the format in existing files.
- `phone`: `207-xxx-xxxx` format matching existing entries.
- `url`: pick **one** prominent link — prefer, in order: official website
  → Facebook page → Instagram → online ordering platform → Google Maps
  listing. Don't invent a link type not actually available.
- `tags`: prefer existing entries from `tags.json` (lowercase form as used
  in other `restaurants/*.json` files, e.g. `"seafood"`, `"waterfront"`,
  `"brunch"`). Only introduce a new tag if nothing in `tags.json` fits and
  it's genuinely reusable across future listings — if so, add it to
  `tags.json` with a fitting emoji **in the same call**, not as a follow-up.
  This is easy to skip when several listings are being researched in
  parallel (each one only sees its own edit, not what sibling batches just
  introduced) — if you're running as part of a batch, still add the tag to
  `tags.json` immediately rather than deferring it, and check whether a
  near-synonym was already added by a different listing in this same run
  before introducing a new one (e.g. don't add `"outdoor dining"` if
  `"outdoor seating"` is already in use).
- `hours`: keys are `mon tue wed thr fri sat sun` (**`thr`, not `thu`**).
  Each value is an array of range strings like `"11 am - 8 pm"` (can hold
  multiple ranges for a split shift/lunch-dinner gap); empty array `[]`
  means closed that day. Match the existing string style exactly (lowercase
  `am`/`pm`, space before them, hyphen with spaces around it).

## 4. Write the file

- New listing: create `restaurants/<id>.json` following
  `templates/restaurant-template.json`'s field order/shape.
- Existing listing: edit only the fields that changed; don't reformat
  untouched fields.
- Leave `restaurants-combined.json` alone.

## 5. Report back

Summarize what changed (or, for a new listing, what you found) and flag
anything uncertain: conflicting sources, seasonal hours in effect, signs the
business may have closed or rebranded, or an `id`/filename/name mismatch you
noticed but didn't fix. Let the user decide on ambiguous calls rather than
guessing silently.
